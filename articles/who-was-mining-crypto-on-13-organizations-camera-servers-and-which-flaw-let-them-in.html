Who Was Mining Crypto on 13 Organizations' Camera Servers, and Which Flaw Let Them In?

Huntress's security operations center watched a GeoVision service start PowerShell on host after host. GeoVision's April advisory had already named three flaws in its WebCam Server.

Style: Brian KrebsStatus: review

WHAT DID THE CAMERA SERVICE DO?

Three PowerShell scripts, labeled a, b, and c, came down from 45.32.117.34. The first ran in memory, searched for writable directories, and checked whether Microsoft Defender was active. The second was written to disk, launched through WMI, repeated the directory probe, and pulled a kernel driver that VirusTotal identified as wsftprm.sys, the driver Huntress calls kvckiller.sys, and one with prior form in bring-your-own-vulnerable-driver attacks, where an intruder supplies a legitimately signed but flawed driver to get around antivirus.

Then came the registry work. Huntress observed three Image File Execution Options hijacks, abusing a Windows troubleshooting feature that lets an administrator point a "debugger" at an executable. The Debugger values for MsMpEng.exe, SecurityHealthService.exe, and SecurityHealthSystray.exe were each set to systray.exe. The likely purpose was to keep Defender's engine, the Windows Security service, and its notification applet from starting.

The third script fetched update.exe, a custom loader written in Go, from 156.246.94.183. That address resolved to cctv-update.top, a domain registered on November 7, 2026, at 02:40 UTC, one day before the main wave. The loader downloaded XMRig and saved it as ApplyUpdate.exe.

WHAT DID THE LOADER LEAVE BEHIND?

The loader is the part of this story that will outlast the mining.

According to Huntress, update.exe carries a BitTorrent Mainline DHT client and a PKARR resolver, which let the operator publish current server addresses under a public key and move infrastructure without registering new domains. Help Net Security put the obvious question to the researchers: was this a mining operation, or a foothold for something else?

"We'd describe the loader as botnet-like: its DHT and PKARR capabilities let the operator find updated server addresses and deliver new payloads," Anthony Gibbs, a security operations analyst at Huntress, told the publication. "The resilience goal is similar to EtherHiding, though the mechanism differs."

Gibbs said the only payload Huntress saw was XMRig. The loader could fetch others, including for selling access, but "we have not seen evidence that access was sold or used for another purpose in these incidents."

Persistence was on a timer: a scheduled task named PackageUpdater that ran C:\WINDOWS\system32\config\systemprofile\update.exe every 15 minutes, and a second task, PackageUpdater_Startup, that ran the loader at boot with SYSTEM rights. GeoVision's November 11 advisory adds artifacts Huntress did not publish, including PackageUpdater.bat, UpdateData.json, and a second vulnerable driver family, WinRing0, registered as the service WinRing0_1_2_0. Some of the file paths in that guide are samples taken from the default D:\CameraDBs camera database location and may vary by installation.

Two hosts from the same campaign may not leave the same artifact list. Worth remembering before anyone calls a machine clean because the miner is gone.

WHICH FLAW OPENED THE DOOR?

Here the record gets thinner, and the thinness matters.

Huntress did not name a CVE, a vulnerability, or a product version in its advisory, and said it had not determined which flaw was used. Help Net Security pressed, and the answer moved the story forward by one careful step. A sample of affected hosts was running GV-VMS 17.4.8.0, a build compiled April 24, 2024. That version predates V17.4.8.58, the fixed release for the V17 branch.

"GeoVision's April 2026 advisory identifies three unauthenticated remote-code-execution vulnerabilities in the WebCam Server functionality affecting this version, making exploitation of a known flaw the most likely explanation," Austin Worline, a senior security operations analyst at Huntress, told Help Net Security.

"We haven't determined at this time, which of the three CVEs was used or confirmed whether GeoVision considered these installations supported," he added.

The three, disclosed by GeoVision on April 27, 2026, in advisory GV-VMS-2026-04-01, are:

  • CVE-2026-42369, an unbounded copy of a base64-decoded string into a 256-byte stack buffer through the gvapi endpoint. GeoVision assigned it a CVSS score of 10.0; the NVD record lists it as CWE-787, an out-of-bounds write, and notes that the WebCam Server binary is compiled without ASLR.
  • CVE-2026-42370, a stack overflow in the WebCam Server login, scored 9.8 by NVD. Cisco Talos's TALOS-2026-2369 traces it to an unsafe strcpy of an unchecked username length in the log_login function, with ASLR disabled across WebcamServer.exe and its DLLs.
  • CVE-2026-7372, an unconstrained sscanf that splits the authorization buffer into 40-character username and password stack variables. Values longer than 40 characters overflow the stack. NVD and GeoVision both score it 9.0; the GitHub Advisory Database record, published May 4, 2026, describes code execution as SYSTEM.

GeoVision's April advisory says all three affect GV-VMS V20.0.2.0 or earlier, V17.4.8 or earlier, and V18.3.5 or earlier, and fixes them in V20.0.2.10, V17.4.8.58, and V18.3.5.22. Its November advisory responding to the XMRig attacks, GV-SFW-2026-11-01, goes further: it describes unauthenticated WebCam Server RCE used to run PowerShell as SYSTEM and deploy the miner, and points customers at the same three CVEs.

What neither Huntress nor GeoVision has published is exploit traffic, exploit code, or a CVE tied to a specific intrusion. A single packet capture, exploit sample, or vendor confirmation would close the question. Until then, the case for the three flaws is strong. It is not closed.

WHAT IS STILL MISSING?

A few loose ends:

Huntress's advisory body says the activity spanned "ten accounts and 13 organizations." Its MITRE ATT&CK table, on the T1190 row, says nine accounts. ThreadLinqs flagged the inconsistency; the advisory does not reconcile the two figures.

NVD's affected-product tables for all three CVEs list only GV-VMS V20.0.2, even though GeoVision's advisory includes the V17.4.8 and V18.3.5 branches. A defender who reads only NVD could conclude that a 17.4.8 installation is out of scope. GeoVision's advisory says otherwise.

Huntress also saw WebCamServer.exe connect to 2.59.133.151 and called that address the "likely source of exploitation," without explaining the direction or purpose of the connection. It is the kind of detail that would settle the initial-access question, and it does not.

One error in the coverage is worth correcting. HashLytics wrote that CVE-2024-6047 and CVE-2024-11120 were Huntress's candidate flaws for this campaign. They were not. Those are 2024 command-injection bugs in end-of-life GeoVision devices, added to CISA's Known Exploited Vulnerabilities catalog on May 7, 2025, with a federal remediation deadline of May 28, 2025. Help Net Security raised them as historical context. The 2026 WebCam Server CVEs are the candidates. The three were not in CISA KEV as of this writing; OpenCVE notes that CVE-2026-42370 is not listed.

WHAT SHOULD A DEFENDER DO TONIGHT?

Patch to GeoVision's current builds: V20.1.3 for V20, V18.3.5.25 for V18, and V17.4.8.65 for V17. The last is cumulative; V17.4.8.58 closed the April flaws, and .65 supersedes it.

Then take the camera server off the public internet. Huntress's advice is a VPN or an IP allowlist. GeoVision lists the ports to restrict: 80, 554, 4550, 5550, 5552, 15552, 3388, 5611, 6550, 6200, and 48000. ThreadLinqs goes further and recommends disabling WebCam Server where it is not required, or restricting it to trusted addresses where it must stay reachable.

Huntress's detection lead is the one I would hand to a tier-one analyst: a command shell or PowerShell session with GeoStartupAgentService.exe as its parent. A camera service has little reason to launch either. Windows Event ID 4688 and PowerShell script block logging, Event ID 4104, will show it if the logs are switched on and retained.

And if the service did launch a shell, do not clean the host. Isolate it, preserve the evidence, and rebuild. An intruder who ran as SYSTEM, loaded a kernel driver, and disabled Defender through registry keys does not leave a machine anyone can trust after a deletion pass.

GeoVision's removal guide goes straight to deletion. Huntress's advice is to preserve evidence first. When two documents disagree about the order of operations, trust the one that assumes the machine is still compromised.
